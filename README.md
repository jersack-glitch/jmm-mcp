# JMM MCP

Custom MCP server for the Jeremy Management Model. Runs as a Supabase Edge Function.

## Setup on a new machine

1. Install Supabase CLI: brew install supabase/tap/supabase
2. Clone this repo: git clone <repo-url>
3. Link to project: supabase link --project-ref <project-ref>
4. Apply migrations: supabase db push (or paste supabase/migrations/*.sql into the SQL editor — they are idempotent)
5. Deploy: supabase functions deploy jmm-mcp

## Structure

- supabase/functions/jmm-mcp/index.ts — the MCP server
- supabase/migrations/ — schema migrations (memory semantic search lives here)
- supabase/config.toml — Supabase project config

## Memory semantic layer

The `memory_semantic_search` migration upgrades the memory table from a
substring-searchable log into a retrieval layer (RAG for the JMM memory):

- **Embeddings** — each memory gets a 384-dim `gte-small` vector, generated by
  this edge function via `Supabase.ai` (built into the edge runtime, no external
  API key). Stored in `memory.embedding` (pgvector, HNSW-indexed).
- **Hybrid recall** — `memory_recall()` fuses vector and full-text keyword
  candidates on a shared relevance scale, then weights by importance (1–5),
  recency (180-day decay), and how often a memory has been referenced.
- **Reinforcement** — recall bumps `last_referenced` / `reference_count` via
  `memory_mark_referenced()`, which feeds back into ranking: memories that get
  used stay fresh, memories that never do decay.
- **Deduplication** — writes check `memory_find_similar()` and flag likely
  duplicates (cosine similarity ≥ 0.86) instead of silently piling up variants.
- **Lifecycle** — `status` (active/archived) + `status_reason`; archived
  memories drop out of recall. The Node servers (jmm-mcp-server) expose
  `update_memory` / `archive_memory` on top of this.

### Function tools

POST the function with `{ "tool": "<name>", "args": { ... } }` (Bearer: anon or
service key, since `verify_jwt = true`):

| Tool | Purpose |
|---|---|
| `add_jeremy_memory` | Guarded write (requires `approved: true`); embeds + dup-checks |
| `add_claude_memory` | Free write to the Claude layer; embeds + dup-checks |
| `recall_memory` | Hybrid semantic recall; `{ query, layer?, tag?, limit?, min_score?, reinforce? }` |
| `embed_text` | Embedding service for the Node servers; `{ texts: string[] }` → 384-dim vectors |
| `backfill_memory_embeddings` | Embed rows where `embedding IS NULL`; `{ batch_size? }`, call until `done: true` |
| `get_priorities` / `get_stalled` | Triage queries (unchanged) |

### Backfill existing memories

After applying the migration and deploying the function:

```bash
curl -s -X POST "https://<project-ref>.supabase.co/functions/v1/jmm-mcp" \
  -H "Authorization: Bearer <anon-or-service-key>" \
  -H "Content-Type: application/json" \
  -d '{"tool": "backfill_memory_embeddings", "args": {"batch_size": 50}}'
```

Repeat until the response reports `done: true`. New writes embed themselves.

Everything degrades gracefully: before the migration is applied (or if
`Supabase.ai` hiccups), writes fall back to the legacy shape and recall reports
what happened instead of failing.
